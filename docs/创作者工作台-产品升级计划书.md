## 0. 执行摘要

项目当前的技术底座已经达标（生产构建、限流、原子写入、每日备份、零源码泄漏、26 项自动化冒烟测试，M2 后为 38 项，M3 后为 44 项，**M4 后为 52 项**）。**但它现在讲述的故事是「我会写全栈」，不是「我懂游戏营销」。**

差距不在功能数量，而在**数据闭环**：

```
今天：  选题（AI 给「预估播放」）→ 脚本 → 发布 → ✂️断✂️ → 账号看板（只有粉丝/均播）
目标：  选题（有品类基准线支撑）→ 脚本 → 发布 → 回填真实结果 → 预测校准 → 反哺下一次选题
```

关键判断：**闭环所需的原料已经全部存在于代码中，只是被丢弃了**——B站接口返回的单条视频数据被 `reduce` 成平均数扔掉（`accountSyncService.ts:132-138`），竞品播放/点赞数据只用于过滤和排序（`bilibiliCollector.ts:158,267`）。

> **M1 完成后的修正（2026-10-05）**：诊断成立，但解法要改。原以为可以直接列出自有视频明细，实测发现 `/x/space/wbi/arc/search` 稳定返回 `-352 风控校验失败`（带 WBI 签名 + `buvid3` cookie 也一样）。因此 M1 改走「用户粘贴链接 → `/x/web-interface/view` 精确取数」。详见 §5 · M1 的「设计变更记录」。

> **M2 完成后的修正（2026-10-05）**：「AI 拍脑袋给播放量」已解决，但解法与原计划不同。原计划用 `ranking/v2?rid=4` 做品类基准，实测该榜单条目**中位年龄 552 天**（冻结快照），且热门池在品类关键词上只命中 0–2 条。最终改用**带时间窗的搜索接口**（`pubtime_begin_s`/`pubtime_end_s` 实测生效）取「近 30 天 · 按播放排序」样本。详见 §5 · M2 的「设计变更记录」。

本计划书把升级拆为 **5 个里程碑、3 个优先级**，其中 M1–M4 是必做项，也是作品叙事的地基。**M1、M2、M3、M4 已完成。**

## 3. 设计原则与硬约束

来自项目已确立的约束，**后续所有改动必须遵守**：

1. **零新增运行时依赖**——前端不引入图表库/UI 库（现有 Recharts 除外），后端不引入新 npm 包。原生实现优先。
2. **纯 ASCII 脚本**——所有 `.bat` / `.ps1` 必须保持纯 ASCII（历史教训：`chcp 65001` + 中文会让 cmd 解析错位，报 `'NODEEXEPORT' is not recognized`）。
3. **不破坏现有契约**——`/api/sync/*` 四态语义、限流头、SPA fallback、`server/public` 生产托管方式不得回退。
4. **数据诚实原则（新增，核心）**——任何展示给用户的数字，必须显式标注来源：
   - `data`：来自真实接口/统计（附样本量与时间窗）
   - `ai`：AI 推断（附置信度或区间，**不得伪装成精确值**）
   - `manual`：用户手填
   - 无来源 → 显示「暂无数据」，**不得用 0 或占位数字代替**（这是 G1 的根源教训）
5. **每个里程碑独立可交付**——不允许「做一半就上不了」。
6. **限速与缓存优先**——B站接口实测有风控（连续调用第二次即返回 `{"code":-352}`），任何新采集必须走缓存 + 限速 + WBI 签名。

## 5. 里程碑详情

### 🎯 M1 · 选题–结果闭环 ✅ 已完成（2026-10-05）

**目标**：给「预测」装上「验证」。

**交付物**

1. 数据模型扩展（`Topic.published` + `TopicStatus` 增加 `'published'`）
2. 「粘贴链接 → 精确取数」的发布结果回填
3. 前端「记录发布」入口 + 「预测校准」视图

#### ⚠️ 设计变更记录（重要，本身也是作品叙事的一部分）

原计划是「自动列出自己账号的全部视频 → 按标题模糊匹配回填」。**实测后放弃了这条路**：

| 接口 | 实测结果（2026-10-05） |
|---|---|
| `/x/space/wbi/arc/search`（列自己的视频） | ❌ 连续两次均返回 `{"code":-352,"message":"风控校验失败"}`，**即使带上 WBI 签名 + buvid3 cookie 也一样** |
| `/x/web-interface/view?bvid=`（单条视频） | ✅ 8/8 成功（0ms 间隔也是 8/8），无需登录、无需 WBI、返回完整 `stat` |

**判断**：与其做一个会静默失败的自动匹配，不如做一条不会撒谎的精确链路——
**用户粘贴链接 → 解析 BV 号 → 直接取那一条视频的真实数据**。副作用是彻底消灭了「标题模糊匹配误配」这一整类错误，也不再需要用户提供 cookie。

这个取舍本身就是营销岗 JD 想要的「关键判断」：**发现方案 A 的数据源不可靠时改走方案 B，并说清为什么。**

#### 验收结果

- [x] 粘贴链接能取回真实播放/点赞/投币/收藏/分享/评论（实测 `views=6,843,038`）

#### 已知限制

- **无法自动列出自己账号的全部视频**（`arc/search` 被风控）。要补这个能力需要用户提供 `SESSDATA` cookie。
- 抖音仍为手动填写（原计划即如此）。
- `Topic.estimatedViews` 原本是「被写成 0 但从未被读取」的死字段，M1 把它变成了有意义的预测值。

#### 复盘：上线后发现的一次线上白屏（2026-10-05）

**现象**：M1 上线后用户反馈「数据看板打开就白屏」。

**定位**：`creator-app/src/pages/Analytics.tsx` 里 `if (!account) return <加载中/>` 是一处 **early return**，而本次新增的 `const calibration = useMemo(...)` 被写在了它**之后**。首次渲染 `account` 为 `null`，React 少调用一个 hook；数据回来后再渲染就多出一个 hook，React 抛 `Rendered more hooks than during the previous render.`，整页崩溃。**双端 `tsc` 全程 EXIT=0** —— 这类错误类型系统抓不到，项目当时也没有 ESLint。

**修复**：把该 `useMemo` 移到 early return 之前。它只依赖 `topics`，与 `account` 无关，本来就不该被 `account` 挡住。

**回归护栏**：新增 `tools/hooks-audit.mjs`（零依赖，约 90 行），静态扫描 `creator-app/src`，检测「任意 hook 调用位于同一组件内 early return 之后」；已接入 `build.ps1` 作为构建前置步骤，不通过则构建失败。

**验证**：护栏先用一份故意写错的 fixture 反向验证它能报错（`useMemo at :11, early return at :7`），再全仓扫描 0 命中；重新构建 + 重启后端后，用无头 Edge 逐路由渲染 6 个页面，root 均非空且无 React 错误串；冒烟测试 **26/26** 通过（本地 + 公网）。

**教训**：`tsc` 通过 ≠ 运行时安全。凡是「新增 hook」的改动，都要检查它是否落在了任何 early return 之后。

| B站 `-352` 风控 | 缓存 TTL 6 小时；刷新接口限流 10 分钟 3 次；采集失败**保留旧缓存** |

#### ⚠️ 设计变更记录（重要，本身也是作品叙事的一部分）

原计划是「拉游戏分区排行榜 → 按 rid 归类」。实测把三条都推翻了：

| 原方案 | 实测结果 | 最终方案 |
|---|---|---|
| 用 `ranking/v2?rid=4&type=all` 做品类基准 | `code:0` 但条目**中位年龄 552 天** —— 这是一份长期冻结的快照，拿来算「当前水位线」会完全失真 | 弃用为基准来源，仅保留作「榜单口径」样本并明确标注 |
| 用 `rssKeywords` 在热门池上匹配品类 | 热门池 130 条游戏内容里，8 个品类命中数只有 0–2 条（热门池是头部大号内容，标题里根本不会出现「独立游戏」这类品类词） | **品类级基准只能走搜索源** |
| 搜索接口没法限时间窗，只能用榜单快照 | `pubtime_begin_s` / `pubtime_end_s` **确实生效**：对照实验 `days=30` → maxPlay 276 万，`days=3650` → maxPlay 3248 万 | 品类线统一用「近 30 天 · 按播放排序」30 条 |

三者叠加得出最重要的结论：**「有哪些数据源」和「哪个数据源能回答这个问题」是两件事。**
排行榜能回答「现在什么在火」，回答不了「恐怖游戏这个品类的正常水位是多少」——
后者需要一个时间窗可控的检索源。这也是 M2 里最值钱的一条判断。

1. **不重采数据，改为把原始样本池落盘。** 标题模式、时长曲线、发布时段三个维度必须在**原始条目**上算，而 M2 的缓存只存了算好的分位。为 M3 重新采集要多打 18+ 次 B站接口、加大 `-352` 风控风险 → 改为把 `popular`（500 条）与 `search`（270 条，带品类 `group`）一并写进 `benchmark.json`，M3 直接在池子上算。旧缓存没有池子，`needsPool()` 并入过期判定后**自动补采一次**，不需要人工清缓存。

#### ⚠️ 设计变更记录（重要，本身也是作品叙事的一部分）

1. **规则引擎和 AI 彻底分家**：原计划是「AI 检查封面文案」，实现时拆成「规则引擎做判断 + AI 只写文案」。理由：判断必须可复现、可审计、离线可用；如果判断也交给大模型，用户没法知道结论为什么是这样，也没法测。

#### 🔧 M4.1 · 上线后修正：面板输入不再丢（2026-10-05 晚，tag `v1.5.1`）

**两个根因（都是真机用出来才暴露的）**

1. **输入不落库**：`creator-app/src/components/PlatformCheckPanel.tsx` 里四个输入是纯组件 `useState('')`，只活在内存里 —— 切脚本或重开页面必然清空。
2. **看起来「不更新」其实是限流**：`server/src/index.ts:62` 的 `app.use('/api/ai', aiRateLimiter, …)`（20 次/分）把**纯规则**的 `/api/ai/evaluate-cover` 一起罩住了，而面板每轮停手会并发发 B站 + 抖音两次请求 —— 打满就 429，面板静默停更。（每日 AI 配额早就豁免了纯规则检查，被漏掉的是分钟级限流。）

**改法**

- 前端：新增 `PlatformCheckInput { coverText, ctr?, completionRate?, postsPerWeek?, updatedAt }` 并挂到 `Script.platformCheck`，输入直接落进脚本记录（Dexie + 云同步 `scheduleSyncUpload` 5s 防抖）；输入即存 + 停手 400ms 自动复查（两次复查之间至少隔 1.5s）；面板加 `key={scriptId}` 防止换脚本串内容；新增「填写完毕」按钮（清掉防抖定时器 + 立即落库 + 立即复查一次）。
- 后端：给 `/api/ai/evaluate-cover` 单开 `coverCheckRateLimiter`（120 次/分）；`useAI === true` 的请求仍走 AI 档与每日配额。

#### 🔧 M4.2 · 上线后精简：删掉只给「参考」的规则行（2026-10-06 凌晨，tag `v1.5.2`）

**用户原话**（随一张面板截图，截图里五行全是「参考」徽标：封面文案：强情绪 / 封面图像：对比度·亮度 / 封面点击率（CTR）/ 更新节奏 / 完播率）：「平台适配度这个功能我觉得要优化，这里面有太多没什么实际意义的东西。图中这几条你就给个参考，一点分析都没有，直接删掉精简界面吧」

**问题定性**：不是「规则太少」，而是**规则里混进了一批根本无法判断、只输出一句通用提醒的行**。这类行越长，面板看起来越像免责声明，越不像检查器。

**删掉的 5 条与各自理由**

| 规则 id | 面板上的样子 | 为什么删 |
|---|---|---|
| `cover-pixels` | 封面图像：对比度 / 亮度 | 本工具只读文案、不分析像素，这条**永远是 info**，是纯粹的说明书 |
| `ctr-reference` | 封面点击率（CTR） | B站/抖音 都没有公开接口，只能手填；口径还是 YouTube 的，横比无意义；不填时又只排一行「不填就不会给结论」 |
| `cadence` | 更新节奏 | 频道级习惯，不是**单条脚本**的平台适配问题，放错位置 |
| `completion-rate` | 完播率分档 | B站恒为「不套用」（噪音），抖音要**发布后**数据才有得比 |
| `platform-coherence` | 平台一致性 | 与时长卡首句（`durationAdvice.detail`）说的是同一件事 |

**保留的 4 条（都能对当前输入给出真判断）**：`title-question`（疑问句，贺一 2023 A 级）、`title-emotion`（标题强情绪词，Cui et al. 2024 A 级，负向）、`cover-emotion`（封面文案强情绪，同一条 A 级研究，正向）、`reverse-list`（标题党反向清单，计划书附录 B C 级）。

**改法（贯穿类型 → 引擎 → 路由 → 前端一条线）**

- 新增一条引擎原则：**拿不到输入的规则直接不出现**。`checkPlatform` 改成 `if (title) rules.push(titleQuestionRule, titleEmotionRule); if (coverText) rules.push(coverEmotionRule); if (title || coverText) rules.push(clickbaitRule)` —— 没填标题就没有标题类规则，没填封面文案就没有封面类规则，`total` 可以为 0。旧的 `info` 占位（「不填就不会给结论」）整体废除。
- 发布后指标**从类型里删掉**，不只是不显示：`server/src/services/platformRules.ts` 的 `PlatformCheckInput`、`creator-app/src/types/index.ts` 的 `PlatformCheckInput`、`creator-app/src/api/client.ts` 的 `evaluateCover` payload 都只剩 `{ platform, title?, coverText?, durationSec? }` / `{ coverText, updatedAt }`。前端「+ 填更多（CTR / 完播率 / 更新频率）」三个输入连同展开按钮一起删除 —— 留着一个改了没反应的 UI 比删掉更糟。旧脚本记录里遗留的 `ctr` 等字段**读时忽略、写时原样保留**（浏览器回归专门断言 `ctr: 4.5` 没被覆写丢失）。
- 抖音的完播率参考线**保留**在 `durationAdvice.completionReference`：它按时长给，不需要用户先有数据，属于「现在就能判断」。
- `server/src/index.ts` 的 120 次/分宽档与条件 AI 档（M4.1 加的）不动。

### 6.1 新增数据结构

```ts
// 发布结果记录（M1 ✅ 已实现于 creator-app/src/types/index.ts）
// 指标字段全部可选：缺失 = 未知。不要用 0 冒充「数据是 0」。
interface PublishedRecord {
  platform: 'bilibili' | 'douyin'
  bvid?: string
  url?: string
  title: string
  publishedAt: number          // 毫秒
  duration?: number            // 秒
  views?: number
  likes?: number
  coins?: number
  favorites?: number
  shares?: number
  comments?: number
  danmaku?: number
  fetchedAt: number            // 取数时间（毫秒）；手动填写时等于填写时间
  source: 'auto' | 'manual'    // auto = 全部数字来自 B站接口
}

// /api/video/stat 返回的单条视频真实数据（M1 ✅ 实现于 server/src/types.ts）
interface VideoStat {
  bvid: string
  title: string
  url: string
  publishedAt: number   // 毫秒（B站 pubdate 是秒，后端已 ×1000）
  duration: number      // 秒
  views: number
  likes: number
  coins: number
  favorites: number
  shares: number
  comments: number
  danmaku: number
  fetchedAt: number
}

// AI 判断的数据出处（强制）
interface Basis {
  source: 'ranking' | 'ai' | 'manual' | 'none'
  sampleSize?: number
  windowDays?: number
  percentile?: number
  confidence?: 'high' | 'medium' | 'low'
}
```

### 6.2 新增 API

| 方法 | 路径 | 说明 | 限流 |
|---|---|---|---|
| GET | `/api/video/stat?url=` | **M1 ✅** 单条 B站视频真实数据（支持 BV 号 / av 号 / 完整链接 / m 站 / b23.tv 短链） | **30/min（独立档）** |
| POST | `/api/video/stats` | **M1 ✅** 批量取数（≤20 条，串行 + 500ms 间隔） | 同上 |
| GET | `/api/report/game-industry?days=30` | **M3 ✅** 生成分析报告（JSON）。不 ready → 503 `NOT_READY`；`days≠30` → 400 `BAD_INPUT` | 继承 `/api/*`（120/min） |
| GET | `/api/report/game-industry.md?days=30` | **M3 ✅** 同一份报告的后端渲染 Markdown（带 `Content-Disposition` 附件头） | 同上 |
| POST | `/api/ai/evaluate-cover` | 封面与平台适配检查（**M4 ✅**；纯规则调用不吃 AI 日配额，`useAI:true` 才调用 AI 润色） | 20/min |

`/api/video/stat` 的返回语义（**M1 的关键设计**）：

- **成功**：`200 { ok: true, stat: VideoStat }`
- **业务失败**：**仍是 200**，`{ ok: false, code, error }`，`code` ∈ `BAD_INPUT` | `NOT_FOUND` | `RISK_CONTROL` | `UPSTREAM` | `NETWORK`。
  用 200 是因为「用户输入不对」不是服务器故障，前端需要拿到结构化错误码做提示。
  **调用方必须处理 `ok: false`，绝不能把「取不到」当成「播放量为 0」。**
- **缺 `url` 参数**：`400`。**未预期异常**：`500`。

### 6.3 缓存策略

| 数据 | TTL | 存储 |
|---|---|---|
| B站热门榜（10 页 × 50 条） | 6 小时 | `server/data/benchmark.json`（原子写） |
| 单条视频数据（`/api/video/stat`） | 5 分钟 | 内存 Map（上限 500 条，写入前清理过期项） |
| 品类搜索样本（近 30 天 × 30 条） | 6 小时 | 与热门榜同一个快照文件，一次性重采 |
| **原始样本池**（M3 起） | 与快照同生命周期（6 小时） | 同一个 `benchmark.json`：`popular`（500 条）+ `search`（270 条，带品类 `group`）。M3 的标题模式 / 时长曲线 / 发布时段必须在原始条目上计算，缓存里只存算好的分位是不够的 |

> M3 的取舍：为报告重新采集要多打 18+ 次 B站接口、加大 `-352` 风控风险，因此改为**把原始样本池一并落盘**（多占约 300 KB 磁盘，换掉一轮风控风险）。M2 的旧缓存没有池子，`needsPool()` 并入过期判定后会**自动补采一次**。
