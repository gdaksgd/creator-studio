判断过程：两个被实测推翻的原计划

  1. 「自动列出自己账号全部视频再按标题匹配回填」→ 放弃。实测 B站 /x/space/wbi/arc/search 稳定返回 -352 风控校验失败（带 WBI 签名与 cookie 也一样），而单条取数接口 8/8 成功。改为「粘贴链接精确取数」，同时消灭了「标题匹配错人」这一类错误。
  2. 「用 B站排行榜做品类基准」→ 放弃。实测榜单条目中位年龄 552 天，是一份长期冻结的快照，拿来算「当前水位线」会失真；而且它答错了问题——排行榜回答「现在什么在火」，回答不了「这个品类的正常水位是多少」。改用可控制时间窗的搜索源。
有哪些数据源，和「哪个数据源能回答这个问题」，是两件事。

数据诚实：写进产品规则，而不是写在免责声明里

每个数字必须有出处

报告里的每个数字都绑定来源、样本量、时间窗与统计方法；拿不到数据就显示「暂无数据」，绝不用 0 或占位数字代替。程序自检统计「无来源数字」，必须为 0。

结论有边界

演示数据明确标注；简报的计划值与复盘结果分栏显示；内容实验设样本门槛，样本不足时拒绝下「成功」结论；报告逐条写明统计局限。

技术栈与部署

技术栈

  • 前端：React 19 · TypeScript · Vite · Tailwind CSS · Zustand · Dexie (IndexedDB)
  • 后端：Node 22 · Express 5 · node-cron
  • 数据：本地优先（IndexedDB），可选 Supabase 账号制云同步

部署与质量

  • 线上：香港轻量服务器（systemd + Caddy）前置 Cloudflare 代理
  • 构建闸门：React hooks 顺序体检 → TypeScript 类型检查 → 生产构建 → CI
  • 运维：每日云端数据备份、访问日志与日报
